## 1. 圈子：创建、审批、邀请撤销、退出

### 现状与缺口
当前只有种子圈子、邀请加入、退出；`joinMode: 'approval'` 只展示文案，`group.join` 直接写 `active`。方案 §3.2/§7.1 要求“可由圈主审批或自动加入，取决于开关”。

### 数据模型
```ts
type MembershipStatus = 'pending' | 'active' | 'left' | 'rejected';

interface Membership {
  groupId: string;
  userId: string;
  role: 'owner' | 'admin' | 'member';
  status: MembershipStatus;
  requestedAt?: string;
  joinedAt?: string;
}
```
- `(groupId,userId)` 唯一；重新申请复用同一条记录，状态从 `left/rejected` 回到 `pending`。
- `invites` 增加 `revokedAt`、`createdBy`；`tokenHash` 唯一，原 token 不落日志。

### API
| 动作 | 请求 | 返回 | 权限 |
|---|---|---|---|
| `group.create` | `name, joinMode` | `groupId` | 登录 |
| `group.join` | `inviteToken` | `status: active/pending` | token 有效 |
| `group.listPending` | `groupId` | `members[]` | 圈主/管理员 |
| `group.reviewMember` | `groupId,userId,decision: approve/reject` | `membershipStatus` | 圈主/管理员 |
| `group.revokeInvite` | `inviteId` | `status` | 圈主/管理员 |
| `group.updateRole` | `groupId,userId,role` | `role` | 圈主 |
| `group.transferOwner` | `groupId,userId` | `ownerId` | 圈主 |
| `group.leave` | `groupId` | `status` | 成员；圈主需先转让 |

### 规则
- 审批模式下 `join` 只写 `pending`，不授予任何故事/图鉴权限。
- 审批通过后写 `active` 并通知申请人；拒绝写 `rejected`，可重新申请但有冷却时间。
- 邀请撤销/过期后不能新加入，但已在 `pending` 的申请仍需圈主处理。
- 退出时弹窗询问“此前发布到该圈子的故事是否继续可见”，默认撤回；作者逐条确认。
- 圈子页展示“待审批”数量；管理员才能看到入口。

### 验收测试
- 审批模式下加入后图鉴仍 `NOT_MEMBER`，审批通过后可读。
- 撤销 token 后加入失败；重复加入不重复计数。
- 非管理员调 `reviewMember`/`revokeInvite` 返回 `UNAUTHORIZED`。
- 圈主退出必须先转让；转让后原圈主变管理员。

## 2. 故事：草稿、revision、编辑重审、删除

### 现状与缺口
当前 `publish` 直接写 `approved/published`，没有 `saveDraft`、`revision` 和编辑流程；方案 02 的 `story.saveDraft/publish(draftId, revision)` 未落地。

### 数据模型
```ts
interface StoryDraft {
  id: string;
  ownerId: string;
  incident: IncidentInput;
  story: StoryInput;
  revision: number;
  updatedAt: string;
}

interface Story {
  // 既有字段 +
  revision: number;          // 乐观锁
  editedAt?: string;
  deletedAt?: string;        // 软删除
}
```
- 草稿不进入图鉴；只有 `publish` 成功后才写 `stories/incidents`。
- 编辑已发布故事：`revision` 不匹配返回 `CONFLICT`；内容变更后 `moderationStatus='pending'`，审核通过前对非作者隐藏新版本（或整体隐藏，二选一，建议整体 pending 更简单）。

### API
| 动作 | 请求 | 返回 |
|---|---|---|
| `story.saveDraft` | `incident, storyDraft, draftId?` | `draftId, revision` |
| `story.publish` | `draftId, revision, visibilityGroupIds, visibility` | `storyId, status` |
| `story.update` | `storyId, revision, story, visibilityGroupIds` | `revision, moderationStatus` |
| `story.delete` | `storyId, revision` | `deletedAt` |

### 规则
- `publish` 必须校验 `visibilityGroupIds` 全部是当前用户活跃圈子；`self` 时为空。
- 撤回与删除不同：撤回保留记录、可重新发布；删除是软删除，作者不可恢复，管理员保留审计。
- 删除/撤回后图鉴统计立即失效；客户端缓存按 `updatedAt` 失效。
- 审核状态：`draft → pending → approved/rejected`；`rejected` 必须给作者可读原因。

### 验收测试
- 草稿不会出现在图鉴；重复 `publish` 同 `requestId` 只生成一条故事。
- 旧 `revision` 更新返回 `CONFLICT`；编辑后重新审核，非作者看不到未审核版本。
- 删除后作者详情 `NOT_FOUND`，图鉴统计减少，其他成员不可见。

## 3. 追加后续（V1.1）

### 现状与缺口
`storyUpdates` 只展示种子数据；没有 `appendUpdate`、频率限制、可见性继承和修订摘要。方案 §4.4 要求“无限次编辑式追加，但建议每天最多 3 条”。

### 数据模型
```ts
interface StoryUpdate {
  id: string;
  storyId: string;
  authorId: string;
  type: UpdateType;
  body: string;
  visibility: 'inherit' | 'groups';
  visibilityGroupIds: string[]; // inherit 时为空
  moderationStatus: ModerationStatus;
  revision: number;
  createdAt: string;
}
```
- 默认 `visibility: 'inherit'`，读取时用原故事的可见范围；扩大范围必须二次确认并写显式 groupIds。
- 保留旧正文摘要（`previousBody?`）供作者查看，不对其他成员展示。

### API
`story.appendUpdate({ storyId, type, body, visibilityGroupIds?, requestId })`
- 返回 `updateId, moderationStatus`。
- 只允许作者；故事已删除/撤回时拒绝（或允许作者补后续，建议拒绝）。
- 每天最多 3 条，按服务端自然日；`requestId` 幂等。
- 文本走与故事相同的内容检查；敏感信息提示但不静默修改。

### UI
- 故事详情作者视角显示“追加后续”；表单含类型、正文（≤140 字）、可见范围（默认继承）。
- 时间线按 `createdAt` 升序；待审核后续只对作者显示“审核中”。
- 其他成员可关注/取消关注该故事更新（应用内订阅，不依赖微信订阅消息）。

### 验收测试
- 非作者调用 `appendUpdate` 返回 `UNAUTHORIZED`。
- 第 4 条/日返回 `RATE_LIMIT`；重复 `requestId` 只写一条。
- 继承可见性正确；显式扩大范围后非原圈成员仍不可见（需二次确认）。
- 撤回/删除故事后后续不再展示。

## 4. 同款经历（V1.1）

### 现状与缺口
没有 `story_links` 集合、`interaction.linkStory` 和 UI；方案 §5.4 要求“同对故事最多一次、可撤销关联”。

### 数据模型
```ts
interface StoryLink {
  id: string;
  storyIdA: string;
  storyIdB: string;
  createdBy: string;
  status: 'pending' | 'accepted' | 'revoked';
  createdAt: string;
}
```
- 规范化 `storyIdA < storyIdB`，唯一索引 `(storyIdA,storyIdB)`，避免 A→B/B→A 重复。
- 只允许同一圈子的故事；跨圈必须双方都可见才允许。

### API
- `interaction.linkStory({ storyId, myStoryId, requestId })` → `linkId, status`。
- `interaction.revokeLink({ linkId, requestId })` → `status`。
- 被关联方收到通知，可接受/拒绝；只有 `accepted` 在详情展示“同款经历”。

### 验收测试
- 同对故事第二次创建返回 `CONFLICT` 或返回已有 `linkId`。
- 非成员/跨圈不可见的故事不能关联。
- 撤销后双方详情都不再展示；通知保留审计。

## 5. 趣味榜单与投票（V1.2）

### 数据模型
```ts
interface Poll {
  id: string;
  groupId: string;
  awardType: 'funniest' | 'gear_save' | 'most_absurd';
  period: string;       // 例 2026-W47
  candidateStoryIds: string[];
  status: 'nominating' | 'voting' | 'closed';
  closesAt: string;
}

interface PollVote {
  pollId: string;
  voterId: string;
  candidateStoryId: string;
  createdAt: string;
}
```
- 唯一索引 `(pollId,voterId,awardType)`；每期每人每奖项一票。
- 候选必须由群主提名且作者同意参选；作者可随时退出。

### API/规则
- `poll.listActive(groupId)`、`poll.vote(pollId,candidateId,requestId)`、`poll.close(pollId)`（圈主）。
- 票数相同显示并列，不生成“AI 裁判”；不按受伤程度、医疗费用、理赔金额排名。
- 禁止分享/拉好友换票；投票结果只按应用内圈子计算。
- 参与奖励只能是纯展示徽章，且不能重复发放。

### 验收测试
- 同一人同奖项第二票 `CONFLICT`；过期投票 `NOT_FOUND`/`VALIDATION_FAILED`。
- 非成员不能投票；未同意参选的故事不能进候选。
- 并列展示、退出评选、关闭后不可投。

## 6. 道具生命周期、徽章与穿戴语义

### 现状与缺口
当前只有 `quantity/expiresAt`；没有 `reserved/consumed/expired` 状态、消耗动作、badge 定义、首次创建奖励、投票/后续奖励。`steel_hip_guard` 有护臀图层但属于 consumable，当前不可穿。

### 数据模型
```ts
type InventoryState = 'granted' | 'owned' | 'reserved' | 'transferred' | 'consumed' | 'expired';

interface InventoryItem {
  // 既有字段 +
  state: InventoryState;
  reservedBy?: string;
  reservedAt?: string;
}

interface ItemDefinition {
  // 既有字段 +
  equipable?: boolean;   // 与 category 解耦：互动护具也可穿
  grantReason?: 'first_avatar' | 'weekly' | 'vote' | 'follow_up';
}
```
- `consumable` 赠礼用所有权转移；使用时 `quantity - 1` 并写 `consumed` 台账。
- 穿戴不消耗数量；收到护具后必须由本人在角色页确认才穿上（方案 §12.3）。
- 徽章 `badge` 永久、不可转让、不消耗、不表达伤情严重程度。

### API
- `inventory.consume({ itemDefId, requestId })` → 剩余数量；仅本人、未过期、数量 > 0。
- `avatar.equip({ slot, itemDefId, expectedVersion })`：允许 `equipable` 的 consumable；校验所有权。
- `inventory.grantFirstAvatar`：幂等，仅一次；`inventory.grantFollowUp`：按故事/更新去重。
- 过期清理任务：`expiresAt < now` → `expired`，写台账，不物理删除。

### 验收测试
- 并发送礼不超发；失败不扣库存（云端事务）。
- 过期道具不能赠送/穿戴/消耗；重复 consume 同一 requestId 只扣一次。
- 收到护具不会自动穿上；本人确认后才改变外观。
- badge 不可转让、不可消耗。

## 7. 举报、审核、拉黑、隐藏事件

### 现状与缺口
当前举报只是说明弹窗，不写库；没有 `moderation_records/reports`、管理员页面、拉黑、隐藏事件。方案 §13 要求上线前形成最小闭环。

### 数据模型
```ts
interface Report {
  id: string;
  reporterId: string;      // 仅后台可见
  targetType: 'story' | 'update' | 'event' | 'avatar' | 'user';
  targetId: string;
  reason: 'harassment' | 'privacy' | 'medical_claim' | 'brand_claim' | 'other';
  detail?: string;
  status: 'open' | 'reviewing' | 'resolved' | 'rejected';
  createdAt: string;
}

interface ModerationRecord {
  id: string;
  targetType: string;
  targetId: string;
  decision: 'hide' | 'remove' | 'warn' | 'restore' | 'ban';
  operatorId: string;
  note?: string;
  createdAt: string;
}

interface Block {
  userId: string;
  blockedUserId: string;
  createdAt: string;
}
```

### API/规则
- `moderation.report({ targetType, targetId, reason, detail, requestId })`：必须能查看该内容；同一举报人/目标/自然日去重；返回 `reportId`。
- `moderation.listQueue`、`moderation.decide`、`moderation.appeal`：仅管理员；写审计。
- 拉黑后双方不再出现在彼此的图鉴/互动/收件箱；不通知被拉黑者。
- 作者可隐藏单条互动事件（`hidden`），不删除事实；收件箱不再展示，统计是否扣除需产品决定（建议保留总数、只隐藏展示）。
- 举报人身份不向被举报人暴露；管理员操作保留审计。
- 申诉只能由内容作者提交，结果通知作者。

### 验收测试
- 无查看权限的用户不能举报；重复举报同一天只写一条。
- 非管理员访问队列/裁决返回 `UNAUTHORIZED`。
- 隐藏/删除后图鉴统计、收件箱、详情按规则更新；申诉记录可追溯。
- 拉黑后互动被拒绝且不出现在双方列表。

## 8. 收件箱合并、忽略、屏蔽

### 现状
逐条事件列表；没有按故事/日期合并，也没有忽略/屏蔽/关闭全部趣味动作（全局关闭已有设置）。

### 规则
- 同一故事 + 同一自然日 + 同一动作合并为一条：“3 位雪友给你的故事送了抱抱”。
- 合并项展开可看原始事件；标记已读作用于合并组。
- “忽略”只影响当前用户收件箱展示，不删除事件；被忽略的事件不再产生未读。
- “屏蔽某人”复用 `Block`；屏蔽后不再收到对方互动通知，历史保留。
- “关闭全部趣味动作”复用 `UserPreferences.allowFunnyActions`，对全部故事生效。

### 验收测试
- 3 条同故事同动作事件合并为 1 条，展开 3 条。
- 标记已读后未读数正确；忽略后不再增加。
- 屏蔽后新互动被拒绝/不通知；取消屏蔽恢复。

## 9. 隐私：匿名外观、头像展示授权、账号删除、数据保留

### 9.1 匿名外观（待产品决策）
V0.1 已脱敏真实 `userId/avatarId/ownerId`，但保留头像外观。小圈子内仍可能通过外观识别。
- 方案 A（现状）：只隐藏昵称，保留外观；文案需写“只隐藏昵称”。
- 方案 B（更强隐私）：匿名故事使用中性头像（固定配色、无装备），作者本人详情可看真实外观。
- 建议 V1 前用 5–20 人测试决定；若选 B，需在图鉴/详情/分享卡片统一替换，且不能通过装备/表情反推。

### 9.2 头像展示授权
- `avatars.privacy` 增加 `visibleTo: 'group' | 'self'`；关闭后其他成员只看到占位头像，不影响故事正文。
- 作者可在设置页批量关闭/按圈关闭；关闭不删除历史互动。

### 9.3 账号删除与数据保留
- `users.status: 'active' | 'deleting' | 'deleted'`；删除请求进入冷却期（如 7 天），可撤销。
- 删除后：昵称/头像匿名化、故事按作者选择删除或保留匿名、互动事件去标识、音频/草稿删除、台账保留最小审计字段。
- 提供“导出我的数据”（JSON）与“删除我的数据”入口；后台任务记录清理结果。
- 保留期限：原始音频 ≤24h（按实际合规）、AI 任务元数据 30 天、举报/审计按法定期限；在隐私指引中写明。

### 验收测试
- 关闭头像展示后其他成员看不到真实外观，作者本人可见。
- 删除账号后无法登录、个人数据不可检索、审计仍可追溯。
- 删除冷却期内可撤销；到期后清理任务幂等。

## 10. Feature flags、预算熔断与紧急开关

### 数据模型
```ts
interface FeatureFlag {
  key: 'AI_ENABLED' | 'INTERACTIONS_ENABLED' | 'GIFTS_ENABLED' | 'POLLS_ENABLED';
  enabled: boolean;
  limits?: Record<string, number>;
  updatedAt: string;
  updatedBy: string;
}
```
- `AI_ENABLED` 关闭后仍允许纯文字投稿。
- `INTERACTIONS_ENABLED` 关闭后所有 `react`/`gift` 返回 `INTERACTION_DISABLED`，图鉴/故事仍可读。
- 预算：`MAX_AI_JOBS_PER_USER_PER_DAY`、`MAX_AUDIO_SECONDS`、`MONTHLY_AI_ESTIMATED_BUDGET`；达到阈值自动停止新任务，保留手工路径。
- 所有开关变更写审计；客户端启动时拉取，服务端每次写操作重新校验（不信任客户端缓存）。

### 验收测试
- 关闭互动后 `react/gift` 拒绝，阅读不受影响；重新开启恢复。
- AI 预算耗尽返回 `BUDGET_EXCEEDED`，文字投稿仍成功。
- 非管理员不能改开关；变更审计可查。

## 11. 埋点事件与隐私

### 事件 schema
```ts
interface AnalyticsEvent {
  name:
    | 'atlas_view' | 'hotspot_click' | 'draft_start' | 'story_publish'
    | 'story_view' | 'interaction_send' | 'gift_success' | 'followup_publish'
    | 'poll_vote' | 'ai_job_submit' | 'ai_job_success' | 'ai_job_fail'
    | 'report_submit';
  userId: string;       // 内部 ID，不落 OpenID
  groupId?: string;
  storyId?: string;
  props?: Record<string, string | number | boolean>;
  createdAt: string;
}
```
- 不上报原始录音、医疗叙述、自由文本正文、手机号/证件号。
- 客户端批量、失败丢弃，不阻塞主流程；服务端按日聚合，保留 90 天（可配置）。
- 方案 §19 的四个观察问题对应看板：理解度（atlas_view→hotspot_click）、无 AI 投稿率（draft_start→story_publish）、互动率（story_view→interaction_send）、回访（inbox/followup）。

### 验收测试
- 事件不含敏感字段；关闭埋点后不发送。
- 匿名故事事件不携带真实作者 ID（用 storyId/合成 ID）。

## 12. 云端契约：错误码、幂等、事务、索引、环境

### 12.1 统一响应
沿用 `{ ok, code, data?, message?, requestId }`；错误码在方案基础上增加：
`INTERACTION_DISABLED`、`VALIDATION_FAILED`、`PENDING_APPROVAL`、`ALREADY_VOTED`、`STORY_LINK_EXISTS`。

### 12.2 幂等范围
- 方案要求“所有写操作 requestId 幂等”。V1 实现时至少覆盖：`publish/gift/claimWeekly/react/appendUpdate/vote/report/join/consume`。
- 唯一索引 `(action, actorId, requestId)`；重复请求返回原响应，不重复写事件/台账。
- `withdraw/avatar/settings` 可用版本号/状态机保证幂等，但仍建议带 `requestId` 便于审计。

### 12.3 赠送事务
按方案 §10.1：身份 → 双方可见性 → 作者许可/可转让/未过期/限频 → `requestId` 去重 → 事务扣减/增加/台账 → 事件/通知 → 返回。事务不可用时用状态机 + 补偿，不能先扣后无保护增加。

### 12.4 索引与环境
- `memberships(groupId,userId)` 唯一；`invites(tokenHash)` 唯一；`stories(authorId,createdAt)`；`interactions(targetId,createdAt)`；`weeklyGrants(userId,weekKey)`；`pollVotes(pollId,voterId)`。
- dev/test/prod 三套云环境；密钥不进仓库；测试数据不复制生产个人数据。
- 客户端缓存按 `updatedAt/revision` 失效；撤回/隐藏后服务端主动失效图鉴缓存。

### 验收测试
- 并发赠礼最多一笔成功；重复 `requestId` 只转移一次。
- 跨圈猜 `storyId` 返回 `NOT_VISIBLE`；非成员图鉴 `NOT_MEMBER`。
- 撤回后图鉴统计与已加载缓存都失效。
- 预算/限频返回正确错误码，且纯文字路径不受影响。

## 13. 性能与可用性

- 图鉴首屏先出骨架（角色轮廓/灰色占位），数据异步填充；素材按视图懒加载，缓存命中不重复下载。
- 头像 chip 使用低分辨率变体；整身图层按需加载，避免首屏下载全部装备。
- 动画资源缺失/低端机/`reduceMotion` 时静态降级；服务端事实不依赖动画完成。
- 目标：普通网络首屏骨架 ≤1s、可交互 ≤2s（需真机实测，不作承诺）。
- 弱网/失败重试有上限；发布/赠礼失败不播放成功动画。

### 验收测试
- 断网/慢网下骨架可见、错误可重试；失败不产生本地“成功”状态。
- 低端机/减少动效下无动画卡顿；静默降级不丢数据。
- 首屏请求数与素材体积符合预算（需 DevTools/真机测量）。
