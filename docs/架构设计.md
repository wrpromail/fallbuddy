# 摔友记 · 架构设计

> 本文回答「系统怎么搭的」。动手实现细节见 [开发说明](开发说明.md)，实现与方案的逐条对照见 [设计对照矩阵](设计对照矩阵.md)，规格缺口见 [V1 设计补充](V1设计补充.md)。

## 1. 设计目标与工程约束

产品定位与边界（方案 §1–§2）直接翻译成工程约束，这是所有架构决策的出发点：

| 产品原则 | 工程约束 |
|---|---|
| 默认私密，可见圈子必须逐个勾选 | 所有读写以「圈子成员关系」为闸门；分享路径不授予任何权限 |
| 匿名仅是展示匿名，后台可追溯 | 服务端保留真实 `authorId`；响应层统一脱敏；客户端拿不到真实 ID |
| 无付费经济，道具免费且可消耗 | 只有发放/转移/消耗台账（ledger），全系统没有金额字段 |
| 不诊断、不按伤情排名 | 枚举中不存在伤情严重度（`impactKind` 是主观情况）；热点只统计故事数 |
| AI 只在创作时调用（V1.1） | V0 零 AI 依赖，纯文字路径永远可用且是主路径 |
| 面向 5–20 人熟人小圈子 | 数据模型按小规模设计：聚合可以全量内存计算，这是 V0 性能取舍的前提 |

## 2. 总体架构

```text
┌────────────────── 微信小程序（miniprogram/，~8600 行含 422 行生成物）──────────────────┐
│                                                                                      │
│  pages/*  7 个页面：视图编排 + view-model 转换，不保存业务状态，刷新即重新拉取          │
│      │   只通过 services/api 调用业务（两处已知例外见 §3）                            │
│      ▼                                                                               │
│  components/*  avatar-rig / skeleton-map / story-card / reaction-bar / item-card      │
│      纯展示组件：properties 进 → triggerEvent 出；规则判断交给服务层                 │
│      ▼                                                                               │
│  services/api.ts —— 门面（10 行）。V0 指向 mock；V1 换云函数适配器，页面零改动          │
│      ├── services/mock/api.ts   22 个入口、6 个域（auth/group/story/avatar/           │
│      │     inventory/interaction/settings）                                           │
│      │     业务规则全部在此：身份 / 权限 / 限频 / 幂等 / 事务 / 脱敏 / 校验             │
│      │     ├── services/store.ts       本地持久化（wx.setStorageSync + 内存回退）      │
│      │     └── shared/validation.ts    发布输入校验（对齐 incident.schema.json）       │
│      ▼                                                                               │
│  shared/*  枚举 / 类型 / 动作 / 道具 / 时间 / 内容检查 / rig 布局                     │
│            rig.generated.ts 由素材脚本生成，人不得手改                                  │
└──────────────────────────────────────────────────────────────────────────────────────┘

辅助管线（scripts/，与小程序本体解耦）：
  素材：rig-art.mjs 几何定义 → build-assets.mjs → 26 个分层 PNG + rig.generated.ts
  预览：build-preview.mjs 跑真实 mockApi → 自包含 preview/index.html（平行 DOM 实现）
  校验：typecheck → 28 项测试 → Schema/不变量 → 素材尺寸 → WXML 静态检查 → 浏览器回归
```

三条硬规则：

1. **页面不认识 `wx.cloud`**，也不保存业务状态——换后端时页面不动。
2. **服务层不接受客户端传入的 actorId**——身份一律取 `state.currentUserId`（V1 为 `OPENID → userId` 映射）。
3. **素材不是二进制黑盒**——由 `scripts/art/rig-art.mjs` 的几何定义生成，改完 `npm run assets` 重新导出。

## 3. 分层规则与已知例外

| 层 | 允许 | 禁止 |
|---|---|---|
| pages | 调 `services/api`、做展示层转换（label/relativeTime）、路由与 UI 状态 | import mock-build、直接改 DbState、保存业务事实 |
| components | 读 properties、抛事件、本地 timer | 调 services、持有业务状态 |
| services/mock | 全部业务规则、读写 store | 被 shared 依赖（依赖方向不可倒置） |
| shared | 纯函数与常量 | 依赖 wx 运行时之外的任何层 |

已知例外（记为债务，V1 收编进门面）：

- `pages/settings/index.ts` 直接 import `store.resetState()`（重置演示数据，破坏「页面只走 api」）；
- `pages/atlas/index.ts` 直接读写 `wx.getStorageSync('shaiyouji.lastGroupId')`（UI 态持久化未封装）。

## 4. 服务层契约

### 4.1 响应信封

所有入口统一返回 `{ ok, code, data?, message?, requestId }`。mock 的 `ok()` 用 `JSON.parse(JSON.stringify(data))` 深克隆，模拟「云端序列化后页面拿不到内部引用」的真实语义——这条要保留到云适配器，防止页面持有可变引用。

### 4.2 错误码

在用 10 个：`UNAUTHORIZED / NOT_MEMBER / NOT_VISIBLE / RATE_LIMIT / INTERACTION_DISABLED / INVENTORY_INSUFFICIENT / CONFLICT / NOT_FOUND / VALIDATION_FAILED / CONTENT_REJECTED`；预留 `BUDGET_EXCEEDED / AI_PROCESSING`（V1.1）。`message` 只面向用户，不泄露内部 ID。

### 4.3 权限闸门

可见性判定收敛为两个函数，所有入口复用：

- `isActiveMember(groupId, userId)`——圈子级闸门（图鉴、成员列表、退出）；
- `resolveStoryGroup(story, preferredGroupId?)`——故事级闸门：仅自己可见直接拒绝互动/赠礼；优先命中调用者所在的可 Visibility 圈子；作者始终可读写自己的故事（即使已退出圈子）。

`story.getDetail` 在此之上做四层校验：发布状态 → 审核状态 → self 可见性 → 圈子成员关系，任一不满足对非作者返回 `NOT_VISIBLE`，不给出详情。

### 4.4 幂等

`operations` 以 `action|userId|requestId` 为键缓存序列化响应，覆盖 4 个有重复副作用的写：`publish / gift / claimWeekly / react`。其余写操作（`withdraw / join / leave / avatar / settings`）靠状态机或乐观锁兜底。

> 边界声明：本地缓存能证明「重试不重复」，**证明不了「并发不超发」**。云端必须换 `(action, actorId, requestId)` 数据库唯一索引 + 事务，`operations` 不是账本。

### 4.5 事务

mock 里全部校验先行、单次内存变更、最后统一 `saveState`——校验失败提前 return 不落盘，等效原子。赠礼顺序（对齐方案 §10.1）：

```text
gift: 身份 → 故事/收礼许可 → 道具可转让/未过期/库存>0 → 每日限频 → requestId 去重
      → 扣减 → 增加 → 台账 → 互动事件 → 通知（单次变更内完成）→ 落盘
```

云端事务能力不足时按方案要求改为操作状态机 + 补偿，不能先扣库存再无保护增加。

### 4.6 限频与时钟

一律服务端时钟（`shared/time.ts`，UTC+8），不信任客户端：

- 互动：同一用户对同一故事「抱抱/转圈/鼓掌合计」每日 ≤3；
- 赠礼：每人每日 ≤3（全局）；
- 周补给：服务端 `weekKey`（ISO 周），`(userId, weekKey)` 唯一，重复领取返回同一 `grantId`。

### 4.7 乐观锁

`avatar.updateAppearance` 校验 `expectedVersion`，不匹配返回 `CONFLICT`；只能穿已拥有且槽位匹配的外观。

### 4.8 匿名脱敏

`anon_<storyId>` 合成作者 ID（按故事生成，跨故事不可关联）。`getDetail` 对 story / incident / updates / avatar / author 五个对象统一脱敏；客户端判断「是不是我」只能靠 `viewerIsAuthor`；赠礼由服务端从 `storyId` 解析真实作者。服务端保留真实 `authorId` 供撤回、风控、举报。

### 4.9 输入校验（V0.2）

`shared/validation.ts` 的 `validateCreateStoryInput` 对发布输入做全量校验：标题 1–24 字、正文 1–140 字、scenario/cause/bodyParts 1–3 个且不重复、全部枚举成员与三个布尔开关的类型检查，对齐 `incident.schema.json`。**mock 与 V1 云函数共用同一份规则**——这是「mock 是可执行规格」的直接体现。

## 5. 数据模型

`DbState`（`shared/db-types.ts`）承载 13 个对齐方案 §9 的集合 + 1 个 V0 新增：

| 集合 | 关键字段 | 备注 |
|---|---|---|
| `users` | `openid`（仅服务端）/ `preferences` | openid 绝不返回客户端 |
| `avatars` | `equipped` / `privacy` / `version` | 版本号乐观锁 |
| `groups` / `memberships` / `invites` | 成员关系只认 `active`；token 只存 hash | V1 加 `pending` 审批态 |
| `incidents` / `stories` / `storyUpdates` | Incident 与 Story 分离 | 事实不被文案编辑覆盖 |
| `inventory` / `ledger` | `quantity/expiresAt`；台账含周补给与赠礼 | V1 加 state 生命周期 |
| `interactions` / `notifications` | 事件只存元数据 + `animationVersion` | 动画可降级回放 |
| `weeklyGrants` | `(userId, weekKey)` 唯一 | 幂等发放 |
| `operations` | `action|userId|requestId` → 响应 | V0 本地幂等缓存，非账本 |

两条实现替代：`item_definitions` 用 `shared/items.ts` 静态配置（V1 集合化）；`reactions` 计数从 `interactions` 派生（人少可接受，V1 用 `dayBucket` 计数文档）。

核心不变量（`npm run validate` 逐条检查）：

- Incident 1–1 Story，一故事多部位时每个部位各计 1 热点，故事总数只计 1；
- `visibility='self'` ⇒ `visibilityGroupIds` 为空、不进图鉴、分享隐藏；
- 每个圈子恰好 1 个活跃圈主，`ownerId` 与成员关系一致；
- 每个装备变体在正/背面都有图层，背包外观都能对应 rig 槽位；
- 种子每次结构变更需递增 `SEED_VERSION`（store 据此失效旧本地数据）。

## 6. 素材与动画体系

```text
scripts/art/rig-art.mjs        几何定义：骨骼/表情/雪服/帽子/雪镜/护臀/阴影，画布 320×480
        ▼
scripts/build-assets.mjs       按 bbox 裁剪 → 2x PNG（透明）→ miniprogram/assets/rigs
        │                     同时生成 miniprogram/shared/rig.generated.ts（热点/锚点/图层表）
        ▼
shared/rig.ts                 resolveRigLayers()：视图×表情×装备 → 百分比定位图层数组
        ▼
avatar-rig 组件                <image> 按百分比叠放，z-index = 图层顺序
```

- 图层顺序：阴影 → 身体 → 雪服 → 护臀 → 头/表情 → 雪镜 → 帽子；
- 装备槽位 `outfit / headgear / goggles / hip_protector`（+`boots` 预留），道具 ID = rig 变体 key，无映射层；
- 热点：正面 11 个、背面 12 个，与方案 §3.3 的 10–12 一致；锚点 11 个；
- 动作协议：`ActionDefinition`（hug/spin/cheer/receive_gift）驱动 WXSS 关键帧，客户端本地播放；
- **降级链**：`reduceMotion` 或资源缺失 → 静态表情 + emoji；服务端事实（事件/库存）从不依赖动画完成；
- 新增一套雪服的完整流程见 [开发说明 §4](开发说明.md)。

## 7. 浏览器预览

`preview/index.html` 是**平行 DOM 实现**（`scripts/preview/` 约 2800 行），不是小程序运行时：

- 存在的理由：本机没有微信开发者工具，预览 + puppeteer 回归让视觉与交互可以独立推进；
- 它证明：热点命中、图层遮挡、抽屉交互、发布表单、动画降级、无 JS 错误；
- 它不证明：WXML 编译产物、原生 `switch`/`scroll-view`/tabBar、真机性能——这些必须 DevTools/真机复核（当前最大验证缺口）；
- 预览与小程序共用同一份种子与素材（`build-preview.mjs` 直接跑编译后的 mockApi），但预览内的发布/互动只写内存。

## 9. V1 云迁移架构

迁移方式：新建 `services/cloud/` 适配器实现与 mock 相同的函数签名，`services/api.ts` 改一行指向。页面与类型不动。每机制对照：

| 机制 | V0 mock | V1 云端必须 |
|---|---|---|
| 身份 | `state.currentUserId` 固定演示用户 | `OPENID → userId` 映射，openid 不回传 |
| 幂等 | `operations` 本地缓存 | `(action, actorId, requestId)` 唯一索引 + 事务 |
| 事务 | 内存单次变更 | 数据库事务；不可用时状态机 + 补偿 |
| 限频 | dayKey 全量扫描 | `reactions` 的 `dayBucket` 计数文档 |
| 聚合 | 全量数组扫描（O(n×m)） | `group_atlas_stats` 物化 + 索引，撤回时主动失效 |
| 校验 | `shared/validation.ts` | 同一份代码引入云函数 |
| 审核 | 发布即 `approved` | `pending → 内容检测 → approved` |
| 存储 | `wx.setStorageSync` 全量落盘 | 云数据库 + 私有云存储（短时签名） |
| 邀请 | 弱随机 token + hash | 加密随机 token + 撤销列表 + 审批态 |

迁移顺序、环境隔离与密钥管理见 [开发说明 §7](开发说明.md)；上线前合规阻断项（主体类目/UGC/隐私/备案）见方案 §18.2，**应在云函数编码之前先核查**。

## 10. 基础组件 01：解剖战损人体（anatomy-web/）

独立于小程序的网页组件（`npm run anatomy` → http://localhost:7788），是小程序「Q 版骷髅图鉴」的解剖级地基。操作手册见 [anatomy-web/README.md](../anatomy-web/README.md)，这里只记架构事实。

```text
browser（public/，ESM 无构建）                         server.mjs（Node，唯一持 key 处）
────────────────────────────────────              ──────────────────────────────
anatomy-data.mjs    14 张解剖卡片 + 记录校验 + 聚合  ←→  GET/POST /api/records（外部注入）
anatomy-art-*-*.mjs 双风格画法（共享原语 + 标准版 + Q 版）  GET /api/health、/api/anatomy
anatomy-rig.mjs      关节角度引擎（16 关节 + 关键帧）   POST /api/ai/explain、/api/ai/roast
anatomy-app.mjs      页面逻辑：热力/面板/流式渲染      （Ollama Cloud SSE → 文本分块转发，
                                                       失败/无 key → 本地模板打字机降级）
```

架构规则：

1. **数据视图无关**：解剖卡片与记录 schema 是纯数据（`anatomy-data.mjs`），渲染只是投影——接 3D 只需新写渲染器；接小程序可把卡片与聚合逻辑原样搬走（web-view 嵌页或数据层降级两条路径）。
2. **双风格同一契约**：标准解剖与 Q 版导出同一接口（`buildBodyMarkup / getOverlays / JOINTS / ACTIONS`），共用一套部位热区与战损语义；动作角度按各风格肢体长度分别校准（标准版手臂 250px 整臂上举会出画，挥手改为肘部带动）。
3. **解剖卡片是 LLM 的唯一事实来源**：讲解 prompt 只由卡片拼装（防幻觉）；调侃另加「只损行为不攻击人身 + 结尾必须安全提醒」的硬约束，匿名记录进 prompt 前脱敏为「匿名群友」。
4. **key 只在服务端**：浏览器永远拿不到 `OLLAMA_API_KEY`（从环境变量或 `OLLAMA_ENV_FILE` 指定的 .env 读取）；响应头 `x-degraded` 诚实标注离线兜底。
5. **无肉眼回归**：`npm run anatomy:qa`（36 项）把 SVG 光栅化后按坐标采样颜色断言（颅骨/髌骨/胸大肌/臀大肌等实心形状内部取色），视觉验证不依赖人眼，画法重构时有硬保护。
