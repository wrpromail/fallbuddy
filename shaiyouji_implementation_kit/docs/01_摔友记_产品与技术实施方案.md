# 摔友记

> **产品定位**：以群体 Q 版骷髅「战损图鉴」为视觉入口，以个人运动故事、Avatar 互动和可消耗趣味装备为社群玩法，以可选的 AI 语音整理为创作辅助的轻量微信小程序。**不提供诊断、治疗、康复、理赔结论或雪场安全评级。**

**一句话介绍**：把运动翻车现场，变成朋友们共同的回忆。

**项目目标**：以独立开发者可控的时间、成本和合规边界，实现可以邀请 5–20 名朋友真实使用的闭环；不以变现为目标，也不追求第一版大规模增长。

**文档读法**：第 1–6 章是产品设计；第 7–15 章是工程实施；第 16–18 章是上线验证与迭代。附录包括参考数据、接口约定和待验证事项。所有金额和配额是设计预算/查询日快照，须在实际开通时复核。

# 1. 名称、品牌与设计原则

## 1.1 暂定名称

- **中文主名：摔友记**，强调「摔」与「友」的关系，不局限滑雪。
- 英文工程代号：`fall-buddies` / 仓库：`shaiyouji-miniapp`。英文名仅为工作代号。
- 备选：**骨友局**（角色 IP 更突出）、**翻车小骨**（游戏感更强）。
- Slogan：**把运动翻车现场，变成朋友们共同的回忆。**

> 名称尚未完成小程序名称占用、商标类别与近似名称的正式核验；公开使用前在微信公众平台及中国商标网核查。

## 1.2 核心设计原则

1. **先好玩，后丰富**：进入即看到可互动的群体骷髅图；15–30 秒可完成一条不使用 AI 的打卡。
2. **故事属于本人**：发布前预览、编辑，选择圈子，随时撤回；AI 不能自动替用户发布。
3. **轻松但不鼓励受伤**：把「差点摔倒」「护具救场」「平安下山的乌龙」「运动小失误」纳入内容；不奖励受伤严重程度。
4. **互动有边界**：对方 Avatar 的动作以本人允许的动作为准；不允许陌生人毁坏他人物品或持续骚扰。
5. **无付费游戏经济**：不充值、不提现、不交易、不做分享换奖励。趣味道具免费、有限、可消耗。
6. **AI 只在创作时调用**：阅读故事、看图鉴、赠送装备、投票与动画回放均不调用大模型。
7. **默认私密、最小收集**：不默认跨群公开；不收集真实医疗档案；不保存第三方微信关系链。
8. **避免版本一依赖不确定的平台能力**：用应用内「圈子」作为群体关系；微信群 `openGId` 能力后续验证。

# 2. 目标用户、核心价值与非目标

## 2.1 目标用户

- 运动爱好者：滑雪、轮滑、骑行、球类等运动中的新手和熟人搭子。
- 群主/组织者：想给群里制造轻松话题、记录共同经历的人。
- 故事参与者：自己不一定受过伤，但会看故事、投票、送虚拟道具、分享乌龙瞬间。

## 2.2 用户价值

| 用户 | 想完成的事 | 产品提供的价值 |
|---|---|---|
| 经历分享者 | 用一分钟记录一次搞笑/惊险的运动经历 | 可视化事件、头像状态、后续时间线 |
| 群友 | 看谁发生了什么、表达关心或调侃 | 点击部位看故事、动画互动、虚拟赠礼 |
| 群主 | 形成一份群体运动回忆 | 战损分布、趣味榜单、雪季盘点 |
| 谨慎的用户 | 分享故事但不暴露隐私 | 圈子可见、匿名展示、脱敏建议、编辑撤回 |

## 2.3 明确不做的事情

- 不提供伤情诊断、医学知识问答、康复方案、事故责任裁定或保险赔付承诺。
- 不做雪场「危险程度排行榜」，V1 不记录具体雪场、雪道和精确位置。
- 不同步真实微信好友列表、微信群成员列表；不默认形成公开内容广场。
- 不做装备商城、充值、现金价值、道具二级市场。
- 不在首版做生成式视频、全身 3D 和复杂角色骨骼物理模拟。

# 3. 产品信息架构与页面清单

## 3.1 一级入口

采用底部 3 Tab：**图鉴**、**我的角色**、**消息**。故事详情、投稿、圈子邀请、背包、投票作为二级页面。

| 路由建议 | 页面 | 核心功能 | 优先级 |
|---|---|---|---|
| `/pages/atlas/index` | 群体战损图鉴 | 正背面切换、热点、头像/贴纸、聚合数量、故事入口 | P0 |
| `/pages/incident/create` | 新建经历 | 背景标签、部位、文字；可选语音入口 | P0 |
| `/pages/story/detail` | 故事详情 | 时间线、Avatar 动画、反应、投票/赠礼入口 | P0 |
| `/pages/avatar/index` | 我的 Avatar | 换装、表情、背包、已发布故事 | P0 |
| `/pages/group/index` | 圈子主页 | 圈子成员、邀请、可见范围、榜单入口 | P0 |
| `/pages/inbox/index` | 互动收件箱 | 谁对我做了什么、重放动画、后续更新 | P1 |
| `/pages/story/updates` | 追加后续 | 添加就医/保险等**亲历**，手动编辑发布 | P1 |
| `/pages/polls/index` | 趣味评选 | 本周最有梗、护具救场、离谱但平安 | P1 |
| `/pages/settings/index` | 隐私与设置 | 互动权限、圈子授权、删除故事/账号 | P0 |
| `/pages/admin/moderation` | 管理（可先内部） | 举报处理、隐藏违规内容、申诉记录 | 上线前必需 |

## 3.2 首次使用流程

1. 用户从朋友分享的卡片进入；展示产品用途，不要求手机号。
2. 云函数读取当前调用身份的 `OPENID`，内部映射为不暴露的 `userId`；用户可以选择默认匿名昵称和原创 Avatar。
3. 通过邀请 token 加入**应用内圈子**（可由圈主审批或自动加入，取决于开关）。
4. 首次进入图鉴展示示例说明与空状态，允许查看已获授权的群体汇总。
5. 用户首次发布时选择「只自己可见」或指定圈子（必须是已有成员）；发布前显示昵称/匿名、内容与互动权限预览。

## 3.3 默认页面的视觉组织

- 顶部：圈子名称、成员数、切换圈子、邀请按钮。
- 核心：Q 版全身骨骼，**正面/背面**两个模式，关节区域贴状态贴纸或小头像。
- 热点：头、肩、手腕、躯干/腰、臀尾椎、膝盖、脚踝等（初版 10–12 个）；多用户占同一热点时显示叠放头像与 `+N`。
- 下方：本周故事数量、最热部位（仅指**故事数量**）、可点击的榜单和最近故事。
- 文案：默认显示「最热话题部位」，不称「最危险部位」；数量统计明确口径。

# 4. 故事与事故背景设计

## 4.1 对象关系

`User 1—1 Avatar`；`User 1—N Incident`；`Incident 1—1 Story`（支持编辑版本）；`Story 1—N StoryUpdate`；`Story N—N Group`（通过显式可见授权）；`Group 1—N Membership`；`Story 1—N InteractionEvent`；`User 1—N InventoryItem`。

其中 **Incident 是结构化的事实/自述事件，Story 是用户确认过的叙事内容**。不论 AI 如何润色，事故字段必须保留事实来源与置信度，不能用生成的搞笑情节覆盖事实。

## 4.2 事故背景字段（V1）

| 字段 | 形式 | 例子 | 备注 |
|---|---|---|---|
| `sport` | 枚举 | `ski_double`、`ski_single`、`inline_skate`、`cycling`、`ball_sport`、`other` | 首发主打滑雪 |
| `scenario` | 单/多选 | 转弯、刹车、平地、上下缆车、排队、碰撞、其他 | 发生背景而不是地点 |
| `selfReportedCause` | 单/多选/未知 | 卡刃、重心失控、速度过快、没注意障碍、原因未知 | **仅用户自述，不作责任认定** |
| `bodyParts` | 1–3 项 | `tailbone`、`wrist_l` | 用于热区统计 |
| `impactKind` | 枚举 | 虚惊一场、轻微不适、停止运动、本人选择不描述 | 不构成医疗严重程度分类 |
| `protectiveItems` | 可选多选 | 头盔、护膝、护臀、手套 | 与 Avatar 的虚拟皮肤分开 |
| `userSummary` | 短文字 | “左转时卡刃，雪地坐了个屁股墩” | 允许不填写 |
| `visibilityGroupIds` | 数组 | `['grp_x']` | 必须逐一勾选，不默认跨群同步 |
| `allowFunnyActions` | 布尔 | `false` | 建议默认关闭，作者可开启 |

**扩展预留**：`venueId`、`slopeId`、`weatherNotes` 在数据契约中可选但首版 UI 不录入，也不展示排名；不得因位置为空导致其他流程失败。

## 4.3 事故描述与故事正文

- 轻量模式：标签 + 最多 140 字 + 预设趣味标题，零 AI。
- 语音模式：允许 15–90 秒口述；后台转写与结构化，作者审阅后发布。
- 所有故事支持「故事标题」「本人描述」「自愿补充的经历」「状态贴纸」。
- 医疗、保险部分仅记录亲历：流程、感受、本人发生的事情；首版不支持上传病历、保险单、身份证明等原始文件。
- 严肃的伤情故事自动减少搞笑标签推荐，作者可明确选择「求安慰」而非「欢迎调侃」。

## 4.4 追加后续

故事建立后允许无限次编辑式追加，但建议频率限制（比如每天最多 3 条），避免刷屏。更新类型 `follow_up`、`insurance_experience`、`clinic_experience`、`equipment_reflection`、`return_to_sport`、`other`。

- 每条后续记录 `createdAt`、`editorId`、`visibilityGroupIds`、`moderationStatus`。
- 默认继承原故事的圈子可见范围；若想扩大范围，必须二次确认。
- 前端可按时间线展示；旧文字保留修订摘要供本人查看，避免争议。
- 他人关注故事更新是一种应用内订阅，不等同微信消息订阅，外部通知只能在平台规则和用户授权允许时实现。

# 5. Avatar 系统设计

## 5.1 视觉方向

- 原创 Q 版骷髅或滑雪小骨头；比例头大身短、色彩明快，无写实伤口与血腥。
- 正面和背面两套标准姿态；状态：开心、惊讶、无奈、求安慰、酷。
- 装备主题可跨运动扩展：头盔/雪镜/雪服/手套/护臀/护膝/鞋/雪板/贴纸。
- 原创**通用形状**装备，不使用未经许可的商标 Logo、特征性产品外观或官方联名暗示。

## 5.2 V1 技术选择

**建议**：先做 `2D 分层图像 + 坐标锚点 + CSS/小程序动画动作`；统一的动作定义和装备层结构以后可迁移到 Canvas 2D。初版不引入重型 3D/Spine 运行时。

角色定义由**共享资产** + **用户状态**组合。示例图层顺序：

1. `shadow` 阴影
2. `body_back` 背面躯体/后侧腿
3. `body` 骨骼身体与关节
4. `outfit` 衣服/护具
5. `hands` 前景手臂
6. `head` 头与表情
7. `headgear` 头盔与雪镜
8. `stickers` 状态贴纸
9. `effects` 动作粒子/emoji

## 5.3 动作协议与锚点

- 标准设计画布：`320 × 480` 逻辑像素，保持比例缩放。
- 锚点：`head`, `neck`, `chest`, `hand_l/r`, `hip`, `knee_l/r`, `foot_l/r`, `ground`；百分比坐标在配置中定义。
- 动作按 `actionId` 分离于事件：`idle`, `spin`, `hug`, `sit_down`, `receive_gift`, `cheer`。
- 播放时以 `ActionDefinition` 驱动动画；客户端本地解析动作，不生成视频文件。
- **降级**：低性能设备、动画资源缺失或用户开启减少动态效果时，改为静态表情/状态贴纸。
- **资源管控**：图像分辨率、透明边距、层尺寸统一；按需加载运动专属装备；资源可采用云存储/CDN，实际小程序包体上限以当前开发工具核验。

## 5.4 他人对 Avatar 的互动

互动必须针对故事或本人自愿公开的 Avatar 状态，不是公开修改对方持久化角色配置。

| 行为 | 动画 | 持久化影响 | 初版限制建议 |
|---|---|---|---|
| 抱抱 | 两角色靠近/爱心浮动 | 增加互动消息 | 同用户同故事/日最多 3 次（各类共享） |
| 转圈 | 对方角色短暂旋转 | 记录事件 | 需作者开启搞笑互动 |
| 鼓掌 | 彩纸/拍手 | 记录事件 | 可默认开启 |
| 赠送护具 | 道具飞向接收者 | **库存所有权变更** | 每人每日赠送最多 3 件 |
| 同款经历 | 两故事连线 | 创建可撤销关联 | 同对故事最多一次 |

作者可关闭「搞笑动作」「陌生圈子成员互动」「接收礼物」，并可隐藏某条事件。举报和拉黑是上线前必需能力。

# 6. 趣味装备、免费获取与投票

## 6.1 物品分类与生命周期

- **外观装扮 `cosmetic`**：基础帽子、雪镜、雪服等，用户永久拥有，不损坏，不转让（首版）。
- **互动道具 `consumable`**：护臀、热可可、创可贴、祝福券等，有限数量，可以赠送或消耗。
- **限定纪念 `badge`**：例如群体活动纪念贴纸，不交易、不消耗、不表达伤情严重程度。

互动道具状态：`granted → owned → reserved → transferred/consumed/expired`，避免直接删除导致账务问题。其 **定义** 是一份全局共享模板；库存仅保存 `itemDefId + ownerId + quantity`，无每个物品的图片副本。

## 6.2 装备获取方案

| 触发 | 奖励 | 防滥用约束 |
|---|---|---|
| 首次创建 Avatar | 基础外观套装 | 一名用户仅一次 |
| 每周免费补给 | 2 件随机互动道具 | 周期唯一键，最多存 8 件 |
| 参与群体投票 | 纯展示纪念标记（可选） | 不奖励重复刷票 |
| 认真追加故事后续 | 可选的小贴纸 | 不与就医/受伤程度挂钩 |

**不做**：连续签到压力、分享好友得道具、看广告兑换、随机付费抽奖、道具充值、装备概率付费。随机免费补给也应公开可选范围，无现金价值。

## 6.3 装备损坏 / 消耗

- `consumable` 赠送时采用**所有权转移**；使用时数量减 1。
- 可设置有效期 `expiresAt`，到期不再活跃；不要用「他人恶搞可打坏装备」设计。
- 耐久度若实现，应当在**本人确认消耗**时扣减；V1 可先用 `quantity` 代替复杂耐久。
- 云函数以事务写入 `inventory_ledger`，幂等操作防重复赠送和并发超发。
- 老物品状态/事件保留有限时间用于审计和纠错，然后按保留策略归档/汇总。损坏本身不会自动降低存储成本。

## 6.4 趣味榜单

默认三种：**本周最离谱但平安的摔法**、**最佳护具救场**、**最有梗运动故事**。群主可从已发布且愿意参选的故事中选择候选，成员每奖项每期 1 票。

- 不按受伤程度、医疗费用、理赔金额排名。
- 排行榜数据只按应用内圈子计算；参与者可以退出评选。
- 若票数持平，显示并列，禁止人为伪造票数或「AI 裁判」假象。
- 禁止以分享卡片/拉好友作为投票资格与奖励条件；防诱导分享。

# 7. 群体关系与可见权限

## 7.1 把群体定义为应用内圈子

微信平台对微信群信息的获取存在接口、场景和能力限制。**V1 不依赖 `shareTicket → openGId` 成功**，改用：

1. 用户创建 `Group`，生成短期邀请 token。
2. 群主把小程序卡片自然分享至已有微信群。
3. 群友点击后，进入圈子加入页，确认加入；必要时管理员审批。
4. 服务端写 `Membership`，此后只根据 `groupId` 和成员关系判定是否可查看。
5. 如果未来平台官方允许并验证了群唯一标识，再作为降低加入摩擦的附加能力，不替换应用内权限系统。

**请注意**：应用内 `Group` 是一个受邀圈子，并不能证明其成员与某微信群完全一致。页面文案建议使用「雪友圈子」而非「自动识别所有群成员」。

## 7.2 可见性矩阵

| 内容 / 操作 | 作者 | 同圈成员 | 非圈用户 | 管理员 |
|---|---|---|---|---|
| 私人草稿 | 读写 | 不可见 | 不可见 | 仅必要的违规处理权限 |
| 圈子故事 | 读写 | 发布授权后只读/互动 | 不可见 | 可按规则隐藏、处理举报 |
| 原始语音 | 本人有限时可取 | 不可见 | 不可见 | 原则上不开放直接访问 |
| 公开 Avatar 外观 | 可编辑 | 可查看 | 默认不可见 | 按处理权限 |
| 背包库存 | 读写 | 只可见明确展示部分 | 不可见 | 系统受控操作 |
| 圈子聚合图鉴 | 可见 | 可见 | 不可见 | 可处理投诉 |

- 同一故事进入多个圈子，必须作者勾选每个圈子。故事分享卡片本身**不授予查看权限**。
- 链接只能带不敏感的 `storyId`/`inviteToken`；绝不携带 OpenID、session_key、真实姓名等凭证。
- 匿名仅是**展示匿名**，后台仍需有受控用户 ID 以处理本人删除、风控与举报。
- 成员退出圈子后立即失去该圈子权限；此前自己授权的故事是否继续在该圈可见由作者显式选择，建议默认询问撤回。

## 9.3 事件驱动与聚合

- 每个被批准且对某圈子可见的故事，对该圈子相关 `bodyParts` 贡献一次 **故事数**；一条故事标注两个身体部位，两个热点各计 1，但该群故事总数仍计 1。
- 群成员数按活跃 `Membership` 去重；「参与人数」按故事作者去重。
- 推荐服务端聚合或物化统计 `group_atlas_stats`，发布/撤回/成员授权变动时更新；V1 人少时也可直接有限分页聚合。
- 不能根据匿名统计精确定位非公开作者；小群体可显示合并统计并控制详情可见。

## 10.1 赠礼服务端事务（关键）

```text
gift(requestId, itemDefId, targetId, storyId):
  1. 根据当前微信 OPENID 确定 actorId，绝不接受客户端 actorId
  2. 校验 actor 和目标都具有目标故事所属圈子的可见/互动资格
  3. 校验故事作者允许收礼，物品可转让、未过期，限频未超
  4. 根据 requestId 查询去重；已成功则返回原结果
  5. 数据库事务：检查发送方数量 > 0；扣除 1；接收方增加 1；写 ledger
  6. 事务成功后创建 interaction_event 与站内通知（需要幂等处理）
  7. 返回 eventId，前端播放 receive_gift 动画
```

若数据库事务能力或限制不满足，需要在单个文档内通过操作状态机与补偿机制实现一致性，不能先扣库存再无保护地更新接收方。服务端失败时绝不播放「赠送成功」。

# 11. AI 语音口述与异步整理

## 11.1 只为创作服务

最低成本的非 AI 路径始终可用。AI 只处理用户主动提交且明确同意的录音/文本；模型输出只能作为草稿。

## 11.2 流程与状态机

```text
RECORDED (客户端完成录音)
  -> UPLOADED (私有临时存储)
  -> QUEUED
  -> TRANSCRIBING (异步 ASR)
  -> REDACTING (规则去标识 + 模型标记潜在敏感字段)
  -> EXTRACTING (结构化 JSON 和一次简短润色)
  -> MODERATING (文本/媒体合规检查)
  -> READY_FOR_REVIEW (返回本人预览，不发布)
  -> APPROVED_BY_USER (本人修改并确认)
  -> PUBLISHED
```

失败分支：`FAILED_RETRYABLE`, `FAILED_FINAL`, `REJECTED`, `CANCELED`, `EXPIRED`。每个阶段记录次数、请求 ID、耗时、估算费用；同一阶段最多重试 1–2 次，带退避，禁止无限重试。

## 11.3 处理建议

- 录音：15–90 秒，客户端限制大小；每人每天最多 3 次 AI 生成，按自然日和账号 ID 限流。
- 上传时显示用途、保存时长与第三方处理说明，满足必要的权限/同意要求。
- 原始音频存私有对象，使用短时授权调用 ASR；处理后按策略删除，默认建议在任务完成或终止后尽快删除（例如 24 小时以内，最终依实际合规和服务要求确定）。
- 语音转写结果先经过规则匹配：手机号、身份证号、详细地址、账户号码等；将可疑片段标注给作者，不能假定自动脱敏 100% 准确。
- 严禁 AI 添加「可能骨折」「某雪场管理有问题」「保险一定赔」等不在口述中存在的事实或专业判断。
- 对医疗/保险经历保留原意，不提供医疗/理赔建议；可建议作者删除不必要的个人信息。
- 文本与上传媒体按照官方适用的安全能力进行审查，发布前还要复核用户手动编辑的内容。
- `ai_jobs` 仅记录安全的元数据，不把未经脱敏的原文或音频 URL 打进普通日志。

## 11.4 LLM 输入与输出协议

输入包含：`transcriptRedacted`, `allowedEnums`, `tonePreference`, `userProvidedTags`；不提供 OpenID、手机号或不需要的用户资料。

输出：

```json
{
  "title": "一次毫无准备的雪地坐姿",
  "body": "转弯时卡刃，直接坐到了雪地上。我决定提前休息。",
  "incident": {
    "sport": "ski_double",
    "scenario": ["turning"],
    "selfReportedCause": ["edge_catch"],
    "bodyParts": ["tailbone"],
    "impactKind": "stopped_activity"
  },
  "privacyWarnings": ["存在可能识别个人身份的详细时间地点，请检查"],
  "requiresUserReview": true
}
```

服务端必须用 JSON Schema 校验；无效字段回退人工选择，绝不将模型输出直接当作可信事件；防 prompt injection，口述内容仅为待整理数据，不可改变服务端规则。

# 12. 互动通知、动画和群体投票实现

## 12.1 事件模型

`InteractionEvent` 不保存视频：`{actionId, actorId, targetId, storyId, itemDefId?, animationVersion, status, createdAt}`。

客户端从 `ActionDefinition` 加载相应动作（如 `spin`、`hug`），通过固定参数播放。旧动作资产升级时，`animationVersion` 保证历史事件可回放或降级显示。

## 12.2 收件箱

- `unreadCount` 和分页 `getInbox(cursor)`；消息在进入应用时拉取，不要求实时 socket。
- 事件按故事/日期合并（如「3 个雪友给你的故事送了抱抱」），避免通知轰炸。
- 支持「标为已读」「忽略」「屏蔽某人」「关闭全部趣味动作」。
- 故事更新可有应用内关注关系，须允许取消；微信订阅消息作为后续能力，遵守用户授权。

## 12.3 动画规则

- 互动产生的动画是展示层效果，不改变目标用户的原始 `AvatarState`；收到护具后也不能自动替其穿戴，需要用户在角色页确认。
- 动画资源加载失败时仍展示文字和库存变更；服务器事实不依赖动画完成。
- 一次互动点击按钮后立即进入 pending，云函数成功返回才播放对应成功动画。

# 13. 内容安全、隐私与审核风险

## 13.1 服务定位不是规避审核的替代方案

虽然产品自称娱乐工具、只在熟人圈传播，但它仍包含用户生成的故事、后续、评论/互动和健康相关叙述。**个人主体是否可承载对应服务，必须依据实际功能及微信当前服务类目/资质要求审核确认**。不能认为只要不做公开广场、替换「受伤」词语就一定能过审。

上线前，在微信公众平台核对：可选类目、个人主体适用范围、UGC 申报与安全审核、隐私保护指引、录音权限、备案要求以及虚拟道具功能的审核口径。必要时调整为更轻量的「状态图鉴 + 预设互动」，或使用符合资质的主体；不要绕过平台限制。

## 13.2 内容边界

| 内容 | 处理策略 |
|---|---|
| 轻松自嘲、原创头像、装备心得 | 正常提供 |
| 对真实雪场/他人的未经证实指责 | 拦截争议性表述、允许举报、人工复核 |
| 就医/保险亲历 | 可选分享，提醒删除敏感个人信息 |
| 诊断结论、治疗建议、理赔承诺 | 产品不生成或背书；视发布内容进行审核 |
| 真实姓名/电话/证件/住址/病历图片 | 尽量不收集，检测并提示删除，严重的拒绝发布 |
| 血腥图、羞辱霸凌、未经本人同意的恶搞 | 拒绝发布/隐藏/处理举报 |

## 13.3 隐私与安全最低要求

1. 在需要时取得有效的隐私授权并完成平台隐私保护指引配置；录音明确说明用途。
2. 以最小必要为原则处理数据；不收集手机号用于普通注册。
3. 将涉及医疗健康等敏感个人信息的处理进行必要性评估，并落实依法需要的单独同意和严格保护措施。
4. 私有音频与草稿由服务端访问控制；原始 URL 不外泄。
5. 作者可删除故事、更新、Avatar 展示授权；提供账号删除路径和后台清理任务。
6. 图片、语音、文字都应进行适用的内容安全检查，包含发布后的用户编辑。
7. 管理/举报操作必须留下受控审计记录，不对普通成员暴露举报人身份。
8. 官方群/朋友关系链 API 不构成隐私权限的替代品。
9. 资产采用原创、不带真实品牌 Logo；品牌名若作为亲历文本出现不得暗示合作或作虚假指控。

> 此章节是工程风险清单，不构成法律意见；实际公开发布应依据上线时的平台规则和现行法律核验。

# 14. 成本预算、限流与断路策略

## 14.1 费用结构

固定项：CloudBase 套餐；可变项：云函数/数据库/存储/网络、语音 ASR、LLM Token、内容安全、潜在图片托管与外发流量。

截至 2026-11-20 官方公开页面显示，CloudBase 个人版存在**¥19.9/月起的限时优惠**，且免费体验版有资源/期限限制；以实际控制台为准。腾讯云 ASR 官网对「录音文件识别（大模型 2.0 版）」展示约 **¥0.8/小时**的后付费价格（具体产品、地区、账户优惠须核对）。

## 14.2 一条语音故事的示意账单

假设 60 秒音频、2000 输入 Token 与 700 输出 Token，用于结构化和润色的**模型价格只是预算参数而非实时确认报价**：

- `ASR = 1 / 60 小时 × 0.8 元/小时 ≈ ¥0.0133`；
- `LLM = 2000 / 1e6 × 输入单价 + 700 / 1e6 × 输出单价`；
- 若临时预算模型使用输入 `¥0.2/M`、输出 `¥0.8/M`，则 LLM 为 `¥0.00096`；两项合计约 **¥0.0143/条**；
- 1,000 条/月约 **¥14.3 的直接 AI 费**，不包含审核、存储、流量、重试与套餐成本。

该示例用于量级判断而非报价承诺。语音计费可能存在时长取整、起步计费或套餐差异，应按实际 API 和账单校正。

## 14.3 预算安全阀

- **不亏本的定义**：不追求收入覆盖成本，而是把月总费用限制在个人愿意承担的范围内。建议初始**目标预算 ¥50–100/月**，设置更严格的 AI 请求上限。
- 由后端维护 `AI_ENABLED`, `MAX_AI_JOBS_PER_USER_PER_DAY`, `MAX_AUDIO_SECONDS`, `MONTHLY_AI_ESTIMATED_BUDGET`；达到阈值自动关闭新 AI 任务，保留手工录入。
- 提供全局配额、单用户限频、同音频内容 hash 去重、短任务超时、失败重试上限和管理员熔断开关。
- 云平台账单告警与预算阈值是**辅助防线**，不能保证所有服务绝不超支；需要对外部按量付费服务分别确认停用/封顶能力。
- 优先缓存一次生成的故事结果，阅读、转发、投票、互动不重算文本。

# 15. 测试与非功能性要求

## 15.1 核心场景测试

- 角色：4 件装备正常分层；正/背面切换；3 个动画；低端设备静态降级。
- 圈子：邀请 token 过期、重复加入、成员退出、非成员通过故事链接查看（必须拒绝）。
- 内容：匿名显示、作者撤回、编辑后重新审核、跨圈不同意不可见。
- 图鉴：一故事多部位统计、一成员多故事计数、图上头像 +N 溢出、空态。
- 互动：关闭搞笑动作后拒绝动作；恶意频繁请求限流；站内消息可重放。
- 背包：免费补给重复点击只发一次；并发送礼不超发；赠礼失败不扣库存。
- AI：失败重试、超时、脱敏提示、预算耗尽降级、音频清理、本人审核后发布。
- 审核：违规拦截、举报、移除、申诉、删除内容后的统计重算。

## 15.2 目标性能与可用性（开发目标，需实测）

- 在普通手机网络条件下，图鉴基础界面优先展示骨架，数据异步加载；首屏目标约 2 秒级，但不承诺不同机型一致。
- 首屏资源保持轻量；头像和装备按需加载、缓存与压缩。
- 主流程即使 ASR/LLM 故障，也可以通过文字模板发布故事。
- 在开发/测试/生产环境使用不同云环境 ID，不把线上个人数据复制进测试库。

# 16. 版本划分与开发路线

## V0：可交互的本地原型（建议先做）

**目标**：无需真实微信身份、外部 AI 或云函数，手机预览即可看到完整玩法。

- 单一原创小骷髅：正/背面静态分层、热区、3 件简单换装。
- 预设 5 条虚构故事、2 个虚拟群、图鉴叠加头像/状态贴纸。
- 本地 3 个互动动作：抱抱、转圈、赠礼视觉演示。
- 数据用本地 mock JSON，优先验证点击热区、层级遮挡、动画协调。

**验收**：一位朋友在不解释的情况下，能点击骷髅打开故事、看到动画并理解「这是一个雪友的故事」。

## V1：真实小圈子闭环

- 接入 CloudBase 登录与用户、创建/加入应用内圈子、故事草稿/发布/撤回。
- 角色外观持久化、群体图鉴统计、故事详情。
- 最简单的反应与消息收件箱、隐私设置、管理/举报基础能力。
- 免费每周道具补给、库存赠送、事务台账；支持文本方式发布故事。
- **先不接 AI**，确保不用模型也能玩。

**验收**：5–20 位受邀朋友能在一个圈子中创建并看到自己的故事，互相赠送道具、返回查看消息；权限测试通过。

## V1.1：AI 与完整故事

- 语音上传、异步 ASR、结构化脱敏、作者检查并发布。
- 追加后续、回访时间线、同款经历关联。
- 真实的预算看板、熔断、删除原始音频和审核工作流。

**验收**：成功语音投稿 20 次以上，人工检查不出现自动发布、敏感内容泄露和事实编造；预算限额生效。

## V1.2：群体玩法

- 趣味榜单提名、投票、同票处理、榜单分享卡片。
- 群体季节回顾、互动动画进一步丰富。
- 无具体雪场事故排行榜。

## V2（仅通过用户反馈后）

- 具体雪场/雪道作为**可选地点标签**，并支持精确地点关闭。
- 角色 Canvas 2D 动画升级、更多运动主题。
- 先完成数据质量、用户授权和品牌/平台风险评估，再决定是否推出按地点浏览故事的功能。

# 18. 决策记录与待验证事项

## 18.1 已形成的产品决策

- **确定**：主入口是群体骷髅图鉴；故事由本人发布；正背面热区；文本零 AI 路径。
- **确定**：V1 不引入具体雪场/雪道；记录事故发生背景与自述原因。
- **确定**：Avatar 是可配置分层角色；动作配置与事件记录独立；接收者可以看到和回放互动。
- **确定**：道具必须拥有才能赠送；免费周期获得；可以消耗或过期；无充值。
- **确定**：故事支持后续追加；群内趣味投票，不做伤情严重程度竞赛。
- **确定**：语音异步处理、自动标记敏感信息、用户确认发布；AI 成本需要额度和熔断保护。
- **建议/待验证**：圈子使用应用内 ID，是否可以绑定官方群标识仅作为增强项。

## 18.2 上线前的阻断问题（Go/No-Go）

1. **主体与服务类目**：当前个人主体能否提供这种私密 UGC/互动服务？是否需要变更定位/主体？
2. **平台接口**：`shareTicket`/群标识的当前可用场景；`chooseAvatar` / nickname、录音权限与安全检测接口能力。
3. **内容安全**：适用的文本/媒体检测接口、UGC 声明、举报与处理链路是否符合审核要求？
4. **个人信息**：隐私保护指引、敏感个人信息处理、第三方 ASR/LLM 合规条款是否明确？
5. **库存事务**：实际所选云数据库是否支持该赠礼事务的操作与隔离；并发压力测试是否通过？
6. **预算**：各产品实际计费粒度、免费配额、告警阈值和是否支持真正的停用上限？
7. **名称/素材**：名称、视觉资产、引用品牌内容是否有权利冲突？

# 19. 首次测试的成功标准

第一批用户建议 5–20 人，邀请以朋友群自然分享，不做任何奖励型强制传播。

**观察四个问题**：

1. 初次见到骷髅图时，能否在 10 秒内理解是「群友故事集合」？
2. 至少一部分参与者是否愿意在没有 AI 的情况下写一条真实趣事？
3. 看完别人故事后，用户是否愿意主动使用「抱抱」「同款经历」「赠礼」中的至少一种？
4. 发布后是否有人愿意返回查看互动消息或追加故事后续？

建议记录匿名聚合指标：`atlas_view`, `hotspot_click`, `draft_start`, `story_publish`, `story_view`, `interaction_send`, `gift_success`, `followup_publish`, `poll_vote`, `ai_job_submit/success/fail`, `report_submit`；不埋点原始录音和个人医疗叙述。

**成功不等于分享数量越大越好**；用户是否感到有趣、愿意回访并相信自己的隐私被尊重，是更核心的验证。
